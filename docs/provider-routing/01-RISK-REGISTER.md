# Provider Routing Risk Register

Audit date: 2026-09-12

Ratings are for automatic failover if implemented on top of the current code. “Gate” means the condition that must be satisfied before rollout.

| Risk | Severity | Current exposure / evidence | Required control and release gate |
|---|---|---|---|
| Double fulfilment | Critical | A timeout, empty response, invalid JSON, or connection reset becomes `ok=false`; the wallet is refunded. Retrying or failing over could cause two providers to fulfil one customer request. | Typed outcomes must distinguish pre-send safe failure from post-send ambiguity. On ambiguity, stop the chain, keep the intent pending, verify with the same provider/reference, and require manual resolution when lookup is unavailable. |
| Double debit | Critical | Debit and transaction creation are separate. A repeated client request has no client-idempotency constraint. | Create a unique purchase intent first; enforce `(actor_id, idempotency_key)` uniqueness; debit once using an idempotent wallet operation/ledger link; return the existing result on replay. |
| Premature refund | Critical | Every adapter `ok=false`, including cURL error, empty response, and invalid JSON, triggers immediate credit (`Vtu_service.php:131-149,243-260,357-373`). | Refund only after a definitive non-fulfilment or verified terminal failure. Ambiguous attempts remain debited/pending. Refund must be compare-and-set and unique per purchase. |
| Provider timeout | Critical | `Vtu_http` has a 10-second connect timeout and default 25-second total timeout. It does not report whether the body was sent. | Record cURL errno, timing, HTTP code, request-send phase, and attempt reference. Timeout-after-send is `AMBIGUOUS`; no automatic next provider. Add provider lookup/reconciliation before any retry. |
| Duplicate provider callbacks | High | Purchase adapters have no callback event ledger or idempotent callback transition. Existing payment webhook dedupe is unrelated. | Authenticate callbacks; store a unique provider event ID/hash; update attempts/intents with atomic legal state transitions; make wallet/referral side effects idempotent. |
| Wrong plan code passed to another API | Critical | `service_pricing.plan_code` is an upstream-specific code. Switching provider visibility is safe only because mismatched plans are hidden/rejected; failover would currently reuse the first provider's code. | Canonical product plus provider-product mapping is mandatory. Resolve a distinct mapped code for every attempt; never carry a provider code across adapters. Block routes with incomplete mappings. |
| Stale pricing | High | Customer debit and `cost_price` come from a mutable pricing row. Analytics may infer legacy cost from the currently active provider. | Snapshot selling price, expected cost, pricing row/version, canonical product, and chosen route on the intent before debit. Validate freshness/activation atomically. Never reconstruct historical cost from current routing. |
| Race conditions | Critical | Wallet debit is atomic, but provider activation, intent creation, provider call, refund, and transaction insertion are not coordinated. Two admins can also race exclusive activation because no database constraint/version exists. | Use immutable route snapshots, optimistic versioning, unique constraints, row locks/atomic updates for intent and circuit transitions, and idempotent side-effect keys. Never hold DB locks across HTTP calls. |
| Provider low balance | High | ADE/MSORG/SMEPLUG detect variants of “insufficient/low balance” and mask the text, but emit untyped `failed`. | Classify explicit provider-wallet rejection as definitive/provider-unavailable only after fixture verification. It may fail over safely if no fulfilment was accepted and product mapping exists; open/degrade the provider circuit and alert operations. |
| Provider authentication failure | High | HTTP status is not globally enforced. A valid JSON 401/403 body may be classified inconsistently; the failure type is lost. | Treat verified 401/403/auth codes as definitive provider-configuration failures, open the circuit immediately, alert, and permit next provider only when the response conclusively rejected the purchase. |
| Malformed upstream response | Critical | JSON parse failure becomes ordinary failure and immediate refund. A provider may have fulfilled before sending malformed output. | Classify as ambiguous after send. Persist raw response safely (redacted/truncated), reconcile by upstream reference, and do not refund/fail over automatically. |
| Database disconnect after long provider call | Critical | `Vtu_service` calls `db->reconnect()` after the provider response, but the durable transaction does not exist before the call. If reconnect or insert fails, fulfilment/debit may exist without a transaction row. | Commit intent and debit state before the call. Use a short post-call transaction to append attempt outcome and advance state. Queue/manual reconciliation must recover from post-call persistence failure. |
| PHP `max_execution_time` | High | App Purchase, dedicated Gateway methods, and result checker set 90 seconds inconsistently; `Vtu_http` assumes a typical 30-second limit and defaults to 25 seconds. Generic gateway handling may not extend the limit. | Centralize time budgets, keep per-attempt timeout below request budget, allow only bounded attempts, and move reconciliation to cron/queue where available. Never start another attempt without enough remaining budget. |
| Shared-hosting constraints | High | The deployment may lack workers, Redis, supervisor, long-running processes, or reliable cron frequency. Synchronous multi-provider calls can exceed proxy/PHP limits. | Database-backed state and leases, short requests, bounded single probe, cron-safe reconciler with overlap lock, no Redis requirement, and an admin recovery view. Validate MySQL/MariaDB version and scheduler availability before rollout. |
| Reference fragmentation | Critical | Orchestration reference is returned/sent upstream; `Transaction_model` generates another stored reference. Dedicated reseller endpoints return none. | One public purchase reference must be created before debit, stored on the intent and transaction, returned on every channel, and used to derive stable per-provider attempt references. |
| Unlogged attempt | Critical | Transactions are inserted only after the provider call, and failed rows omit provider/ref metadata. | Persist intent and attempt before send; record provider, mapped product, request reference, start time, transport result, normalized outcome, and redacted response. |
| Unsafe status normalization | Critical | ADE maps every unknown status to failed; MSORG treats a 2xx response with no status/error as completed; SMEPLUG documents pending but never emits it. Non-2xx HTTP is not inherently rejected by `Vtu_http`. | Provider-specific, fixture-tested outcome parsers; unknown/missing/conflicting states become ambiguous, never completed or definitively failed. HTTP status and business status are separate fields. |
| Unsupported adapter dispatch | Critical | UI says ADE supports cable/scratch card, but ADE's generic method shapes all non-airtime requests as data. Generic Gateway offers scratch-card/result-checker through the same path. | Capability registry enforced server-side. Refuse unsupported provider/service pairs. Add service-specific adapter methods and contract tests before enabling a route. |
| Missing status lookup | Critical | No purchase adapter implements lookup. Pending transactions can only be manually completed/refunded. | Verify upstream APIs and implement lookup by attempt reference/provider ID. Services/providers without lookup cannot automatically recover ambiguous outcomes and must have a manual SLA. |
| Circuit-breaker stampede | High | No circuit state exists. A naive implementation could send many half-open probes. | Atomic `OPEN -> HALF_OPEN` lease, one probe owner, expiry, and compare-and-set transitions. Other requests skip the provider while the lease is held. |
| Bad circuit signal | High | Business validation failures could incorrectly count against provider health. | Count only provider/transport failures designated as circuit-relevant. Customer input, unsupported product, and local wallet errors do not affect provider health. Ambiguous transport outcomes may open/degrade but must not trigger failover. |
| Route misconfiguration / no service default | Critical | Target hierarchy requires a default but no rule schema exists. Optional override-only configuration could leave traffic unroutable. | Transactional publish validation: exactly one enabled service-default rule, contiguous priorities, enabled configs, capabilities, and complete product mappings. Reject invalid drafts. |
| Route changes during purchase | High | Current active state is read live at several points. | Resolve and persist an immutable route snapshot/version once per intent. Later admin edits apply only to new intents. |
| Credentials at rest and in logs | High | Provider tokens are database plaintext. `Vtu_http` logs full response bodies, which can contain tokens/PINs/customer data. | Restrict DB/endpoint access, encrypt secrets where hosting supports a separate application key, redact structured logs, never log PIN/token payloads, and define retention/access controls. |
| Referral side-effect duplication | High | Completed transaction creation immediately invokes referral rewards; later manual completion can invoke it again, relying on downstream uniqueness. | Drive rewards from a unique completion event/ledger key after an atomic terminal transition. Treat duplicate invocation as a tested no-op. |

## Failover release blockers

Automatic failover must remain disabled until all of the following are true:

1. One durable reference and intent exists before any wallet or network side effect.
2. Outcome taxonomy and provider parsers are fixture-tested.
3. Ambiguous outcomes stop the chain and enter reconciliation.
4. Every failover-enabled data product has complete provider-specific mappings.
5. Provider idempotency and lookup capabilities are verified against authoritative documentation/sandbox tests.
6. Service-default routes are validated and published atomically.
7. Circuit transitions and half-open lease behavior pass concurrency tests.
8. App and reseller traffic demonstrably use the same orchestrator.
9. Refund/debit/callback actions are idempotent under replay and worker overlap.
10. Schema drift is resolved and migration dry runs pass on the actual hosting database version.
